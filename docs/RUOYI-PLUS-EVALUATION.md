## 1. 结论摘要（先给判断）

**RuoYi-Vue-Plus 6.X 是真实且活跃的项目，官方 React 前端也确实存在，PostgreSQL 支持有实际 SQL 脚本。** 上一轮我判断「不迁移」时，确实没把 React 版本算进去，这一点需要修正。

**但我依然不建议直接进入正式迁移**，理由不是框架不好，而是：

1. 真正的工作量不在「有没有后台管理页面」，而在 **Java 与 Python 两套身份体系怎么打通**；
2. 那 24 张表、Umi Max 前端、Sa-Token 会话，都是新增的运维与学习成本；
3. 6.0.0 是 2026-07-30 才发布的大版本（SpringBoot 4.1 全生态升级），距今不到 3 个月。

**建议**：按你的思路做隔离 POC，但**先把 no-go 条件写死**（见 §7），5 天内跑不通就回退到已经设计好的 pwdlib + Casbin 方案。否则 POC 很容易变成「先搭起来再说」，一路沉没成本。

## 2. 事实核查（与上一轮的差异）

### 2.1 后端

| 项 | 核查结果 |
|---|---|
| 仓库 | `dromara/RuoYi-Vue-Plus` |
| 许可证 | **MIT**（LICENSE 文件 1,081 字节） |
| 默认分支 | `6.X` |
| 最新发布 | **v6.0.0**，2026-07-30 发布，非预发布 |
| 活跃度 | 2,793★ / 799 fork，**最近推送 2026-10-20**（当天） |
| 定位 | 重写 RuoYi-Vue 的后台系统，集成 Sa-Token、MyBatis-Plus、WarmFlow、SpringDoc、Hutool、OSS |

**6.0.0 的重大变化**（来自官方 release notes，影响评估结论）：

- **不兼容升级到 SpringBoot 4.1 全系列**；
- **整体移除多租户**（第 9 条）——如果未来想按「学院」做租户隔离，框架不再提供；
- 新增 `ruoyi-snailai-server`（AI Agent 平台）、`ruoyi-common-mcp`、`ruoyi-common-mqtt`、`ruoyi-common-elasticsearch`、LiteFlow 规则引擎；
- JDK 升至 21.0.12，Redis 8.6.3，MySQL 8.4.9。

> 注意：仓库 description 仍写着「多租户后台管理系统」，但 6.0.0 已移除多租户。**以 release notes 为准**，这是容易被旧描述误导的地方。

### 2.2 React 前端：位置与上一轮认知的差别

| 项 | 核查结果 |
|---|---|
| 是否存在 | **存在**，但**不是一个独立仓库** |
| 真实位置 | `CrazyLionCat/plus-ui` 仓库的 **`6.X-React` 分支** |
| 包名/版本 | `plus-ui-react`，`6.0.0` |
| 许可证 | MIT（仓库级） |
| 技术栈 | React **19.3**、antd **6.6.3**、**@umijs/max 4.7**、TypeScript **6.0**、Zustand 5、TanStack Query 5、ahooks 3.10 |
| 工程要求 | `engines: node >= 20.19.0, pnpm >= 10`，`packageManager: pnpm@10.34.5` |
| 维护者 | 个人账号 `CrazyLionCat`（版本作者），非 dromara 组织仓库 |

**三点必须写清楚**：

1. `plus-ui-react` 是**分支名/产品名**，不是可以 `git clone plus-ui-react` 的独立仓库；找不到仓库不代表不存在，我一开始也判断成「官方没有」。
2. 它用 **Umi Max + antd 6**，不是纯粹的 Vite SPA，也不是 antd 5。我们现有 3 个页面**不能直接拷贝**，要按 Umi 的路由/请求约定重写。
3. 仓库在个人账号下（前端历史一直如此），MIT 许可没问题，但**长期维护依赖单一维护者**，这是选型的事实，不是贬损。

### 2.3 PostgreSQL 支持

| 项 | 核查结果 |
|---|---|
| SQL 脚本 | `script/sql/postgres/` 下有 4 个：`postgres_ry_vue.sql`、`postgres_ry_job.sql`、`postgres_ry_workflow.sql`、`postgres_ry_ai.sql` |
| `ry_vue` 规模 | **24 张表**，94 KB |
| schema | **没有 `CREATE SCHEMA`**，表名不带前缀（`sys_user`、`sys_menu`…）→ 落在默认 schema |
| 扩展依赖 | **无** `CREATE EXTENSION`（不需要 pg_trgm、uuid-ossp 等） |

**结论**：PostgreSQL 能用，且不需要装扩展。但**必须用独立数据库**，因为 24 张表会建在 `public`，而我们现有库的 `campus` schema 是业务表、`public` 基本为空但归 `campus_dba` 所有。

## 3. 与现有系统的兼容性差异

| 维度 | 现有系统 | RuoYi-Vue-Plus 6.X | 差异性质 |
|---|---|---|---|
| 语言/框架 | Python 3.12 + FastAPI | Java 21 + SpringBoot 4.1 | **异构** |
| 前端 | React 18 + Vite 6 + antd 5 | React 19 + **Umi Max** + antd 6 | **不同工程体系** |
| 认证 | 无 | Sa-Token | 新增 |
| 用户/角色 | 无表 | `sys_user` / `sys_role` 等 24 表 | 新增 |
| 数据权限 | 无 | 部门树 + 角色-菜单-数据权限 | 模型不匹配（见 §5） |
| 审计 | PG 触发器（与业务同事务） | `sys_oper_log`（应用层 AOP） | **两套日志** |
| Schema | `campus.*` | 默认 schema | 需隔离 |
| 部署 | 4 容器（web/db/api/appsmith） | 再+2（Java、Redis） | 运维面扩大 |
| 导入引擎 | Python（解析/映射/校验/状态机） | 框架无此能力 | **必须保留** |

## 4. 复用 / 迁移 / 改造三段划分

### 4.1 可直接复用（省下的就是这部分）

登录、登出、用户管理、角色管理、菜单与动态路由、部门、岗位、字典、参数、通知公告、文件/OSS、在线用户、操作日志、登录日志、缓存监控、代码生成器。

**这部分是真实收益**：按我此前 pwdlib + Casbin 方案自建，至少需要 5–8 天工作量。

### 4.2 必须迁移（改造成本）

| 页面 | 现状 | 迁移到 Umi Max 的工作 |
|---|---|---|
| 总览 | Vite + antd5 | 重写为 Umi 页面，图表可复用 ECharts 封装 |
| 学生查询 | 表格 + 筛选 + 抽屉 | 重写请求层（`@umijs/max` request）、权限指令 |
| 数据导入 | 四步流程 + 映射表 | 重写交互，业务逻辑仍调 Python API |

### 4.3 必须改造（最容易低估）

1. **身份桥接**：FastAPI 如何信任 Java 签发的会话？
2. **审计一致性**：Java 写入走 `sys_oper_log`，Python 写入走 PG 触发器，两套日志如何统一口径？
3. **数据范围**：框架按 `sys_dept` 树过滤，我们的学院是 `campus.students.college_name` 字符串，需要建立「学院 ↔ 部门」映射并在两层同时生效。

## 5. 关键风险

| # | 风险 | 说明 | 严重度 |
|---|---|---|---|
| 1 | **双身份源** | 两套后端、两套会话；若桥接方案不成立，等于白迁 | **高** |
| 2 | 数据权限模型错配 | `sys_dept` 树 vs `college_name` 字符串；可能要改框架授权层 | 高 |
| 3 | 审计断链 | 两套日志，未来查「谁改了这个学生」要跨系统拼 | 高 |
| 4 | 6.0.0 太新 | 发布不到 3 个月，SpringBoot 4.1 生态仍在磨合 | 中 |
| 5 | Umi Max 学习/改造成本 | 不是「复制页面」而是「按 Umi 约定重写」 | 中 |
| 6 | 24 张表进 `public` | 与现有库共库会污染；必须独立库 | 中 |
| 7 | 维护者集中 | React 前端在个人账号分支，单人维护 | 中 |
| 8 | 前端 antd 5→6 | 组件 API 有差异，现有代码不能直接搬 | 低 |

## 6. 与「轻量方案」的对比（pwdlib + Casbin）

| 维度 | RuoYi-Vue-Plus 方案 | pwdlib + Casbin 方案（已设计） |
|---|---|---|
| 新增服务 | +Java、+Redis | 无 |
| 新增表 | 24+ 张（框架自有） | 3 张（auth_user/auth_session/auth_policy） |
| 现成后台页面 | **有，且完整** | 需自建 2 个页面 |
| 身份一致性 | 需跨语言桥接 | 天然一致（同一进程） |
| 审计一致性 | 需统一两套日志 | 沿用现有触发器 |
| 预计周期 | POC 3–5 天 + 迁移 2–3 周 | 实施 1–1.5 周 |
| 长期维护 | 跟进上游大版本（SpringBoot 4.1） | 自维护，代码量小 |

**这不是「哪个更好」，而是「哪条路径的失败成本更低」。** 如果最终只需要四类角色 + 三张页面，轻量方案的确定性更高；如果后续要扩成完整后台（公告、字典、文件、工作流、代码生成），框架的收益才会真正体现。

---

## 7. POC 的 no-go 条件（提前写死）

出现以下任一情况，**停止迁移，回退轻量方案**：

1. 身份桥接（Java → Python 可信身份）需要**超过 3 天**定制改造；
2. PostgreSQL 24 张表脚本需要**修改超过 10 处**才能跑通；
3. 必须把现有 `campus` 业务表迁进框架 schema 才能共用；
4. 学院级数据范围无法用「部门树 + 映射表」表达，需重写框架授权层；
5. POC 启动后 **5 个工作日**内仍无法完成「登录 → 访问一个受保护接口 → 身份传到 Python → 审计记录正确」这一条最小链路。
