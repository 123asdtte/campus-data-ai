### 1.3 数据库账号权限（实测）

| 角色 | 属性 | students | student_changes | import_batches | import_issues | operation_logs |
|---|---|---|---|---|---|---|
| `campus_app` | 非超级、可登录 | SELECT/INSERT/UPDATE | SELECT/INSERT/UPDATE | SELECT/INSERT/UPDATE | SELECT/INSERT/UPDATE/**DELETE** | SELECT |
| `campus_ro` | 非超级、可登录 | SELECT | SELECT | SELECT | SELECT | SELECT |
| `campus_dba` | **超级用户** | 全部 | 全部 | 全部 | 全部 | 全部 |

- `campus` schema 的 ACL 中**没有 PUBLIC**，普通角色无权访问（良好）。
- 5 个序列对 `campus_app` 授予 `rU`（读 + 使用），**无 UPDATE**。
- **没有默认权限（pg_default_acl 为空）**：未来新建的表默认不会自动授权。
- `.env` 中存在 `RO_DB_PASSWORD`，但**当前没有任何服务使用 `campus_ro`**（实测连接里没有该用户）。

### 1.4 Appsmith 的实际连接（关键发现）

`pg_stat_activity` 实测：

```
campus_app | Appsmith JDBC Driver | 172.20.0.4 | idle
```

**Appsmith 正以 `campus_app` 身份直连业务库**，而该账号对 students、student_changes、import_batches 拥有 INSERT/UPDATE。

含义：

- Appsmith 上的任何 SQL 查询/表单，可以**绕过 Import API** 直接改学生数据；
- 写操作仍会触发审计触发器，但 `actor_user_id` 取决于 Appsmith 是否设置 `campus.actor_user_id` —— 当前 Appsmith 不会设置，因此这些操作在审计中**无操作人**；
- `campus_app` 没有业务表的 DELETE 权限，所以 Appsmith **删不掉**学生，但可以**改**（例如批量修改学院/状态）。

### 1.5 可信操作人与审计现状

| 项 | 现状 |
|---|---|
| 操作人来源 | 前端 `VITE_ACTOR`（默认 `local.operator`）→ `X-Actor` 请求头 → `_actor()` 仅做长度截断 → `set_config('campus.actor_user_id', ..., true)` |
| 是否可信 | **不可信**。任意客户端可伪造 `X-Actor: 校长` |
| 数据库层面 | `audit_row()` 触发器读取 `current_setting('campus.actor_user_id', true)`；`operation_logs.actor_db_role` 记录真实 DB 角色（**这一项可信**） |
| 敏感字段处理 | `audit_payload()` 会剔除 `id_card_no`、`phone_no`、`home_address`、`family_info` 四列（当前表中并无这些列，属预留） |
| 实际数据 | 544 条审计中，**504 条 `actor_user_id` 为空**（501 条 insert + 3 条 update，来自种子数据与直连写入），25 条 `demo.teacher`、10 条 `web.ui`、2 条 `local.operator`、2 条 `import.test`、1 条 `demo.teacher` update |
| 审计写入时机 | 触发器在业务事务内同步写入，**与业务操作同事务**（这一点设计正确，无需改） |

## 2. 认证方案设计

### 2.1 学校侧情况

学校官网「综合服务」栏目下**存在「统一身份认证登录」入口**（`skzyxy.com/zhwf/zhfw2`），说明校内已有统一身份认证平台。但：

- 未公开对接协议（CAS / OAuth2 / OIDC / LDAP 未知）；
- 未公开是否允许第三方系统接入、是否需要走信息中心审批；
- 本机环境无法直接访问校内认证服务。

**结论：SSO 是首选终态，但当前不具备实施条件，需学校信息中心确认。**

### 2.2 候选方案比较

| 维度 | A. 自建本地账号 + 服务端会话 | B. 学校统一身份认证（SSO） | C. Nginx Basic Auth | D. JWT 存 localStorage |
|---|---|---|---|---|
| 实现成本 | 中（一张用户表 + 会话表 + 登录页） | 高（需对接协议、审批、网络打通） | 低 | 中 |
| 是否需新服务 | **否**（复用 FastAPI + PostgreSQL） | 否（但需校外网络可达） | 否 | 否 |
| 能表达角色/数据范围 | 是 | 是（需映射校内属性） | **否**（只有账号维度） | 是 |
| 可撤销/可登出 | 是（会话表可失效） | 是 | 否（改密码才能踢） | 差（无状态难撤销） |
| 与现有审计集成 | 好（会话里直接取 user_id） | 好 | 差（拿不到工号） | 中 |
| 前端凭证暴露风险 | 无（HttpOnly Cookie） | 无 | 浏览器弹窗，无 | **高**（XSS 可读） |
| 适用阶段 | 内网试点、当前阶段 | 正式上线 | 临时保护 | 不建议 |

**推荐：以 A 为实施主线，同时预留 B 的适配层。**

理由：当前是内网 + 虚构数据阶段，A 能在不新增服务的前提下补齐身份、角色、审计三件事；B 的协议一旦确认，只需把「登录入口」换成 SSO 回调，用户表与角色表可复用。

### 2.3 推荐方案的技术要点

| 项 | 设计 |
|---|---|
| 账号来源 | 本地 `auth_user` 表：工号、姓名、角色、所属学院、状态、密码哈希 |
| 密码存储 | **Argon2id**（`argon2-cffi`），内存 64 MB、迭代 3、并行 4；禁止 SHA256/MD5 |
| 会话 | 服务端会话表 `auth_session`（token 只存 SHA256 摘要），Cookie 名 `sid` |
| Cookie 属性 | `HttpOnly` + `SameSite=Lax` + `Path=/`；生产加 `Secure`（需 HTTPS） |
| 有效期 | 绝对 8 小时 + 空闲 30 分钟滑动续期；登出即删除会话行 |
| CSRF | `SameSite=Lax` 覆盖大部分场景；对 POST 追加 **双提交 Token**（`X-CSRF-Token` 与 Cookie 比对）+ `Origin` 校验 |
| 登录失败限制 | 同一账号 5 次失败锁定 15 分钟；同一 IP 15 分钟内 20 次失败拒绝；记录失败审计 |
| 未登录请求 | 统一返回 `401 {"detail":"未认证"}`；前端拦截跳登录页 |
| 角色校验 | FastAPI 依赖项 `require_role([...])`，按路由声明 |
| 数据范围 | 依赖项返回 `scope_college`，查询时强制拼接学院条件（待业务确认是否按学院隔离） |
| HTTPS | 生产必须；本机可先用 HTTP，但 `Secure` 关闭并明确标注「仅限本机」 |
| SSO 预留 | 登录逻辑抽象为 `authenticate()`，SSO 回调只要产出同样的 user_id 即可复用会话与授权 |

**不引入**：Keycloak、Auth0、OAuth2 Proxy 等新组件 —— 与「不重写、不新增服务」的约束冲突，收益不足以抵消运维成本。

|---|---|---|---|---|
| 查看学生列表/详情 | 全部 | 本学院（待确认） | 全部（待确认） | 全部（只读） |
| 查看学籍异动 | 全部 | 本学院 | 全部 | 全部 |
| 查看看板统计 | 是 | 是 | 是 | 是 |
| 上传并预览导入 | 是 | 是（限学生/异动） | 是 | **否** |
| 提交导入 | 是 | 是 | 是 | **否** |
| 调整字段映射 | 是 | 是 | 是 | **否** |
| 修改学生基础信息 | 是 | **否**（只允许通过导入） | **否** | **否** |
| 删除学生/异动 | **否**（当前无接口） | 否 | 否 | 否 |
| 导出数据 | 待确认 | 待确认 | 待确认 | 待确认 |
| 查看审计日志 | 是 | 否 | 否 | 是 |
| 管理账号与角色 | 是 | 否 | 否 | 否 |

**明确禁止而非默认开放**：

- 业务角色**不能**直接改学生记录（只能走「导入 → 校验 → 提交」），从源头保证可追溯；
- 只读审计角色**不能**触发任何写接口；
- 任何角色都**没有**物理删除能力（数据库层也未授予 DELETE）。

**待业务确认**：学院级数据隔离是否必要；若需要，需明确「学工/教务人员跨学院查询」是否放行。

## 4. 可信操作人与审计链路设计

### 4.1 目标原则

1. 操作人身份**只从已认证会话**取得，不读任何客户端自报字段；
2. 每次业务写入在同一事务内落一条审计，包含：真实 user_id、DB 角色、动作、对象、变更字段、结果；
3. 数据库连接账号（campus_app）与真实业务操作人（auth_user.id）**分开记录**（现有 `actor_db_role` 字段已支持）；
4. 审计载荷继续剔除敏感列，禁止把身份证号、电话、住址写进日志。

### 4.2 现状与目标的差距

| 要求 | 现状 | 差距 |
|---|---|---|
| 身份来自会话 | 来自 `X-Actor` 头 | **必须替换** |
| 操作人可信 | 可任意伪造 | 高 |
| 写入必须有操作人 | 允许空（501 条为空） | 需触发器强制 `actor_user_id IS NOT NULL` |
| 会话→DB 上下文 | 手工 `set_config`，依赖调用方自觉 | 需统一封装，避免漏设 |
| Appsmith 写入审计 | 无操作人 | 需禁止 Appsmith 写，或强制其设置 actor |
| 敏感字段 | 已剔除 4 列 | 保持；新增敏感列需同步维护 |

### 4.3 设计

```
浏览器 --(HttpOnly Cookie sid)--> FastAPI
   FastAPI: 解析会话 → user = {id, role, college, status}
   每个写请求: 同一事务内
      set_config('campus.actor_user_id', user.id, true)
      执行业务 SQL
      触发器写 operation_logs（actor_user_id / actor_db_role / action / changed_fields）
   commit
```

- 会话解析封装成依赖项，业务代码不再接收 `X-Actor`；
- 写接口在事务开始处设置 actor，失败回滚时审计一并回滚（保持一致）；
- 登录、登出、登录失败单独记入 `operation_logs`（action 扩展为 `login`/`logout`），便于追溯暴力尝试。

## 5. 绕过前端路径的风险分析

| 路径 | 现状 | 风险 | 处置 |
|---|---|---|---|
| 直接调 8010 API | 无认证 | **高**：可读写全量数据 | P0：全部路由加会话依赖；写接口加角色校验 |
| 经 8082 调 API | 无认证 | 同上 | P0：同上（nginx 只做转发，鉴权放后端） |
| Appsmith 直连 DB | `campus_app` 可写 | **高**：可批量改学生，且无操作人 | P0：数据源改用 `campus_ro`；或停用写查询 |
| 伪造 `X-Actor` | 完全可行 | 中：审计失真 | P1：移除该机制，改会话 |
| DB 端口 55432 | 仅 127.0.0.1，但口令在 `.env` | 中：本机任意进程可用 | P1：定期轮换口令；`.env` 权限收紧 |
| Docker 网络内互访 | 同网段可直连 8000/5432 | 中：任一容器被控即可横向 | P2：按服务拆分网络 |
| 局域网访问 | 全部绑 127.0.0.1 | 低（当前） | 保持不变；上 HTTPS 前不得放开 |
| CORS | 未配置中间件（默认同源） | 低：curl 不受限，但浏览器跨站受限 | 保持默认，不新增宽松 CORS |

## 6. 建议实施顺序与验收标准

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| **P0 收口** | ① Appsmith 数据源改为 `campus_ro`（只读）或停用写查询；② 确认 8081 仍可登录；③ 记录改造前的权限快照 | Appsmith 执行 `UPDATE campus.students` 返回权限错误；学生数据未变 |
| **P1 身份** | ① 新增 `auth_user`、`auth_session` 两表；② 登录/登出/会话校验接口；③ 登录页与前端会话处理 | 未登录访问 `/students` 返回 401；登录后可访问；登出后旧 Cookie 立即失效；连续 5 次错误密码被锁 15 分钟 |
| **P2 授权** | ① 全部路由挂认证依赖；② 写接口按角色过滤；③ 移除 `X-Actor`/`VITE_ACTOR` | 只读审计账号调用 `/imports/{id}/commit` 返回 403；普通账号无法调用管理接口；`X-Actor` 不再影响审计 |
| **P3 审计** | ① actor 来自会话；② 触发器强制非空；③ 登录事件入审计 | 任取一次导入提交，`operation_logs.actor_user_id` 等于登录工号；手工构造空 actor 写入被拒 |
| **P4 SSO** | 按学校信息中心确认的协议接入，替换登录入口 | SSO 登录后角色与本地账号一致；回退到本地账号可用 |

**顺序理由**：P0 不依赖任何新代码就能关掉最大的绕过面（Appsmith 可写）；P1–P3 才涉及代码与表结构变更。

## 7. 需学校/业务负责人确认的问题

1. 学校统一身份认证的协议类型（CAS / OAuth2 / OIDC / LDAP）与接入流程？
2. 是否允许本系统作为第三方应用接入，需要哪些审批与安全评估？
3. 角色归属由谁维护：人事/学工/教务，还是本系统管理员？
4. 学工、教务人员是否需要**按学院隔离数据**？跨学院查询是否放行？
5. 导出功能是否必要？若必要，允许导出哪些字段、是否需要审批与水印？
6. 审计日志保留多久？是否需要独立的日志库或只读账号导出？
7. 真实数据接入的前置条件（等保要求、数据脱敏规则、留痕要求）？
8. Appsmith 的定位：保留为只读分析工具，还是最终下线？
