# 校园数据管理与 AI 助手平台 PRD

**版本：** V1.0  
**日期：** 2026-10-20  
**阶段：** 本地验证版（MVP）→ 校内试点版  
**目标用户：** 项目负责人、AI 编程助手、开发人员、信息中心/学工/教务业务代表

> **一句话目标：** 使用 Docker 在 Windows 电脑上搭建一套轻量、可自定义网页的校园数据管理工具。Appsmith 负责页面与数据库操作，PostgreSQL 作为唯一的校园业务主数据库，Dify 负责 AI 工作流与知识库。第一阶段只使用虚构数据；通过验证后再评估迁移到学校批准的内网环境。

## 0. 文档使用方式与关键约定

本文件既是产品需求文档，也是 AI 编程助手的执行规格。实现时必须先完成阶段 0 环境检查，再按阶段逐步交付，不得一开始生成大量未经验证的代码或重写不相关项目。

### 0.1 已确认的决策

| 项目 | 决策 |
|---|---|
| 页面构建 | Appsmith，自定义工作台、表格、筛选、表单、按钮和图表 |
| 校园业务数据库 | PostgreSQL；学生、学籍异动、导入批次等业务数据统一存放于该数据库 |
| AI 平台 | Dify，自建工作流、知识库与聊天应用，通过 API 与工作台集成 |
| 容器运行 | Docker Desktop + WSL2 + Docker Compose（Windows 本地验证）；校内部署阶段优先评估 Linux 服务器 |
| 初始数据 | 仅使用虚构测试数据，不接触未经批准的真实学生信息 |
| 系统定位 | 辅助管理 Excel 数据、查询与导出；不替代青果教务系统、现有学工系统或学校正式审批流程 |
| 旧资料 | 不依赖 WorkBuddy 资料库中的 HTML、CSV、页面或代码；新建独立项目目录 |
| 业务主数据库 | 仅一个 PostgreSQL 业务库。Appsmith 与 Dify 为运行自身所需的内部元数据、缓存等，可能各自带有依赖服务；这些不能用来存放校园主业务数据 |

### 0.2 必须明确的技术边界

1. Appsmith 在本地试验阶段可以直接连接 PostgreSQL，通过参数化查询完成 CRUD。
2. Dify 第一阶段只处理虚构数据和获准公开/非敏感的制度材料，不直接连接业务主数据库，也不得直接执行任意 SQL。
3. 第一阶段如需稳定解析 `.xlsx`，可增加一个非常薄的 Python/FastAPI 导入服务，仅用于解析、校验、预览与提交导入；不要为此引入完整 Java 微服务体系。
4. 真实学生数据接入前，必须重新评估身份认证、角色/行级权限、审计、备份、日志和数据流向。若 Appsmith 当前部署版本的权限能力不足，须先增加受控 API 层或其他经过学校认可的权限机制，不得以“页面上隐藏按钮”代替后端授权。
5. “装在本地”不等于“所有数据都留在本地”。必须检查 Dify 模型端点、知识库嵌入模型、文件解析、外部 API、Appsmith 出站连接与日志配置。


## 1. 背景与问题

学校学工和教务日常存在多个 Excel 分散维护、字段不统一、重复录入、缺失值和重复记录难以及时发现、标准报表重复加工等问题。现有 AI 工具可以辅助表格工作，但若将真实学生数据交给未获学校批准的云端工具，会引发数据安全和责任边界问题。

项目需要一个轻量的本地验证方案，先让业务人员通过网页管理结构化数据，再按需接入 AI。系统应能逐步扩展学工、教务及后续财务相关功能，但一期必须控制范围，避免变成一个未经规划的“大而全校园系统”。

## 2. 产品目标与非目标

### 2.1 一期目标

- 在 Windows 本机通过浏览器打开 Appsmith 工作台。
- 连接唯一的校园业务 PostgreSQL 数据库，实现学生信息和学籍异动的查询、新增、编辑、逻辑停用/删除。
- 支持 CSV 与 XLSX 文件的导入预览、字段匹配、重复与缺失检查、异常报告和人工确认后导入。
- 支持按条件查询、分页、详情查看和标准化 CSV/XLSX 导出。
- 在工作台内提供 Dify AI 助手入口，完成制度问答和一般业务辅助；第一阶段不让 AI 自动修改业务数据库。
- 使用虚构样例完成端到端验收，并留下可重复运行的部署、备份、恢复和测试说明。

### 2.2 一期不做

- 不替换青果教务系统、学工系统、用友财务系统或其他正式系统。
- 不对接未开放的业务系统 API，不做跨系统自动同步。
- 不上传或批量导入未经学校授权的真实身份证号、手机号、家庭住址等敏感信息。
- 不开发完整审批引擎、消息通知平台、移动端小程序、统一身份认证或多租户 SaaS。
- 不让 AI 自主完成退学、休学、转专业等业务数据的正式变更，不让 AI 自主审批。
- 不在一期部署本地大模型。Ollama 为可选后续评估项。
- 不将 Appsmith 或 Dify 的内部元数据库作为校园业务主数据库。

### 2.3 成功指标

| 指标 | 一期验收目标 |
|---|---|
| 环境启动 | 按 README 完成启动，无需手工修改源码 |
| 数据 CRUD | 学生与学籍异动记录的新增、查看、编辑、逻辑删除/停用均可用 |
| Excel 导入 | 100 行虚构样例可预览、发现测试中预设的异常，并在确认后导入有效记录 |
| 数据约束 | 学号唯一约束生效；重复、缺失、类型异常可被识别并展示 |
| 导出 | 筛选后的结果可以导出；导出列与选定模板一致 |
| AI 接入 | Appsmith 能调用 Dify 测试应用并显示回复；API Key 不出现在浏览器可见代码/页面中 |
| 安全边界 | Dify 没有业务数据库直连凭证；测试环境不对公网开放；真实数据入口被明确禁用或标记为未批准 |
| 可恢复性 | 能按说明备份并恢复 PostgreSQL 测试数据 |


## 3. 用户与权限

一期以单机验证为主，至少设计以下逻辑角色。实际能否使用 Appsmith 某版本的内建权限能力，应以所选版本功能核实；如无法实现可靠隔离，则仅允许项目管理员操作测试数据，不进入真实业务试点。

| 角色 | 一期职责 | 允许操作 | 禁止操作 |
|---|---|---|---|
| 系统管理员 | 部署与配置 | 配置连接、管理应用、备份/恢复、管理测试账号 | 不得把测试环境直接当成生产环境 |
| 业务管理员 | 学工/教务测试人员 | 查询、新增、修改、导入、导出虚构数据 | 不得更改系统连接和密钥配置 |
| 只读查看者 | 演示或审核人员 | 查询、筛选、查看详情、查看导入报告 | 不得新增、修改、删除、导入或导出未经授权的数据 |

**正式试点前权限要求：** 学工、教务的授权范围需要由学校确认；仅靠隐藏控件或前端判断不算安全边界。生产上线前应进行越权测试，验证用户无法通过修改请求或 SQL 参数读取/改写未授权数据。


## 4. 总体技术架构

### 4.1 逻辑架构

```text
浏览器
  └── Appsmith（自定义网页、表格、搜索、表单、图表）
       ├── PostgreSQL 数据源：仅用于本地虚构数据的初期 CRUD
       ├── Dify API 数据源：调用 AI 聊天/工作流
       └── 可选 Campus Import API（Python/FastAPI）：XLSX 解析、校验、导入预览

PostgreSQL（唯一校园业务主数据库）
  ├── students
  ├── student_changes
  ├── import_batches
  ├── import_issues
  └── operation_logs

Dify（独立服务栈）
  ├── AI 应用与工作流
  ├── 已审批知识材料
  └── Dify 自身运行所需元数据/缓存依赖（不得作为校园业务库）
```

### 4.2 组件职责

| 组件 | 负责 | 不负责 |
|---|---|---|
| Docker Desktop / Compose | 运行容器、网络、卷和环境配置 | 不自动保证安全，也不替代备份 |
| Appsmith | 搭建页面、表单、表格、查询和 API 调用 | 不作为业务数据库，不代替后端权限审查 |
| PostgreSQL | 业务记录持久化、唯一约束、事务和关联关系 | 不存放 Dify 内部运行元数据 |
| Dify | AI 问答、工作流、知识检索、调用受控 HTTP 工具 | 不作为学生主数据库，不直接执行任意 SQL |
| Campus Import API（可选轻服务） | 解析 XLSX、字段映射、校验、导入预览与确认提交 | 不做通用微服务平台，不接受任意路径或任意 SQL |

### 4.3 连接规则

- Appsmith 使用 PostgreSQL 数据源连接业务数据库。初期必须使用独立的最小权限账号，不使用数据库超级用户。
- PostgreSQL 容器默认不发布给宿主机以外的网络；容器之间使用 Docker 内部网络访问。
- Appsmith 的数据库连接密码存放在 Appsmith 数据源配置中，由服务端管理；禁止写进页面文本、客户端 JavaScript、Git 仓库或截图。
- Dify API Key 必须保存在 Appsmith 的服务端 API 数据源/安全配置中，禁止放入浏览器端可读取的代码、URL 参数或前端变量。
- Dify 不直连 PostgreSQL。未来确需 AI 查询业务数据时，只能调用白名单业务 API；第一期不开放 AI 自动写入业务数据。
- Docker 镜像必须固定可追踪版本或发布标签，不使用不可控的 `latest` 作为正式试点版本。

### 4.4 简化原则

- 不引入 Kubernetes、独立 Redis（除 Appsmith/Dify 官方栈自身依赖外）、Java 微服务、复杂消息队列或本地大模型，除非后续有明确需求。
- 开发者可先用 Appsmith 原生 PostgreSQL 数据源实现基础 CRUD。
- 对 XLSX 复杂解析，如 Appsmith 原生能力不足，仅增加一个窄范围导入服务；不要因此重建整套后台。


## 5. 功能需求

优先级定义：P0 = 一期必须交付；P1 = 本地 MVP 后、校内试点前完成；P2 = 后续扩展。

### 5.1 工作台首页（P0）

- 展示系统名称、当前环境（本地测试/试点）、数据说明和最后更新时间。
- 提供功能卡片：学生信息、学籍异动、Excel 导入、导入异常、统计报表、AI 助手、系统说明。
- 首页统计仅针对测试数据库，至少展示学生记录数、异动记录数、待处理异常数、最近导入批次。
- 每个卡片跳转到真实功能页面，不得链接到空页面或无效占位页面。

### 5.2 学生信息管理（P0）

- 支持分页查询，默认每页 20 条；可选 20/50/100 条。
- 支持按学号、姓名、学院/系、专业、班级、在校状态筛选；文本搜索需要防止 SQL 拼接注入。
- 支持新增、编辑、查看详情。
- 学号为必填且唯一；姓名为必填；状态使用受控选项。
- 逻辑停用学生记录；存在关联学籍异动时，不允许直接物理删除。
- 页面显示操作成功/失败提示；失败时保留用户已输入内容并显示可理解的错误。
- 初始数据字段遵循最小必要原则，不默认设置身份证号、手机号、住址、家庭成员等敏感字段。

### 5.3 学籍异动管理（P0）

- 支持异动记录列表、分页、筛选、详情、新增、编辑、逻辑停用。
- 异动类型初始受控选项：休学、复学、退学、转专业、转学、保留学籍、其他；允许管理员调整字典，但变更需记录。
- 支持按学号/姓名、异动类型、所属班级、发生日期范围、记录状态筛选。
- 每条异动必须关联学生记录；学生不存在时不得导入为正式异动。
- 记录状态仅用于本工具的数据整理，默认：草稿、待复核、已确认、已退回；不得宣称等同学校正式审批状态。
- “已确认”代表业务人员确认本工具内的记录，不代表已同步到青果或已完成学校审批。

### 5.4 Excel/CSV 导入（P0）

- 支持 `.xlsx`、`.csv`；单次文件建议上限 10 MB、10,000 行，限额需可配置。
- 导入流程：选择文件 → 选择目标数据类型 → 识别/映射列 → 预览前 20 行 → 运行校验 → 展示异常摘要与逐行异常 → 人工确认 → 写入数据库 → 生成导入报告。
- 初始模板必须提供“学生信息模板”和“学籍异动模板”，包含字段说明、格式样例和必填标记。
- 校验内容至少包括：必填字段缺失、学号重复、未知学生、无效日期、无效状态/异动类型、超长文本、列名缺失、重复文件/重复批次提示。
- 导入不得直接覆盖全表；必须先在预览阶段完成校验。异常行默认不导入；用户可下载异常明细后修正重传。
- 点击“确认导入”后采用事务提交；若提交失败，应整体回滚或明确显示成功/失败行数，不能静默部分写入。
- 保留原始文件的策略由管理员配置。初期默认只保存必要导入元数据与校验结果，不长期保存包含个人信息的原始文件；测试环境可使用虚构文件留档。
- 每批次需有唯一批次 ID，记录文件名、文件哈希、总行数、有效行数、异常行数、创建时间、操作人和处理状态。

### 5.5 异常处理（P0）

- 单独页面展示导入异常，支持按批次、级别、异常代码、字段、处理状态筛选。
- 每条异常显示文件行号、字段名、异常原因和建议动作。
- 初始异常代码：`MISSING_REQUIRED`、`DUPLICATE_STUDENT_NO`、`UNKNOWN_STUDENT`、`INVALID_DATE`、`INVALID_ENUM`、`DUPLICATE_BATCH`、`COLUMN_MAPPING_REQUIRED`、`VALUE_TOO_LONG`。
- 用户可以标记“已处理”或“需业务确认”，但不得通过标记状态绕过强制字段和唯一性校验。

### 5.6 查询、统计和导出（P0）

- 统计卡片基于数据库实时/准实时聚合，不硬编码数字。
- 至少提供：按异动类型统计、按月份统计、按学院/系或班级统计。
- 允许按当前筛选条件导出 CSV；XLSX 导出作为 P0（若 Appsmith 无可靠原生导出能力，使用导入服务的对应导出接口实现）。
- 导出文件只包含用户当前筛选且有权查看的字段；导出前显示记录数和字段清单，确认后执行。
- 导出操作需记录日志，日志不保存不必要的敏感数据副本。

### 5.7 Dify AI 助手（P0 基础接入；P1 数据工具）

**P0：**
- 在 Appsmith 首页提供“AI 助手”页面或侧栏。
- 调用 Dify 已发布的聊天应用或工作流 API，显示用户提问和 AI 回复、加载状态、错误提示。
- 初始知识库只能使用虚构样例、公开制度或已明确批准的非敏感资料。
- API Key 必须保存在服务器端受保护的连接配置中；不能让浏览器通过页面源代码读取密钥。
- 不把真实学生表、带有学生姓名/学号的记录自动发送给云模型。

**P1：**
- 如需 AI 帮助查询业务数据，增加白名单、只读的业务 API；仅提供必要字段与限制后的聚合结果。
- AI 对数据库的新增/修改只能通过业务 API 提交“待确认操作”，由用户检查差异并二次确认；一期不开发此能力。
- 需要记录调用时间、调用场景、结果状态与耗时；避免在日志中记录完整敏感提示词或学生数据。

### 5.8 系统配置和操作记录（P0 基础）

- 提供数据字典/枚举说明与系统版本信息。
- 记录新增、修改、停用、导入、导出等关键业务动作的时间、操作者、对象、动作和结果。
- 修改前后值只记录必要字段；在真实环境中，日志查看需受限且有保留期限。
- 不要求一期在 Appsmith 内重做完整的账号中心；使用自托管 Appsmith 的账号与应用授权能力。版本权限能力无法满足时，不开放真实数据。

| UI-07 | 导入批次与异常 | 批次列表、异常明细、状态筛选 | 查看报告、下载异常明细 | 能追溯到源文件行号和批次 |
| UI-08 | 统计报表 | 指标卡、柱状图/折线图、筛选器 | 筛选、导出 | 改变筛选后图表和数据同步变化 |
| UI-09 | AI 助手 | 聊天窗口、提示、错误重试 | 调用 Dify | 连接失败不影响 CRUD；无密钥泄露 |
| UI-10 | 系统说明 | 版本、部署状态、安全提醒、字段字典 | 查看配置与说明 | 明确标识“本地测试/虚构数据” |


## 7. 数据库设计（一期）

### 7.1 设计原则

- PostgreSQL 为业务主数据的唯一权威来源。
- 使用主键、唯一约束、外键、事务与时间戳；不使用一个大 JSON 字段代替所有业务字段。
- 学号是学校场景内的业务标识，不要把姓名当唯一键。
- 不默认采集身份证号、手机号等额外敏感信息；如业务确有必要，必须另行确认合法性、用途、权限、存储和保留期限。
- 业务记录优先逻辑停用，不建议物理删除历史业务数据。

### 7.2 表结构

#### `students` 学生信息

| 字段 | 类型 | 规则/说明 |
|---|---|---|
| `id` | BIGSERIAL | 主键 |
| `student_no` | VARCHAR(32) | 必填、唯一、去除首尾空格 |
| `student_name` | VARCHAR(100) | 必填 |
| `college_name` | VARCHAR(100) | 可空 |
| `major_name` | VARCHAR(100) | 可空 |
| `class_name` | VARCHAR(100) | 可空 |
| `enrollment_year` | SMALLINT | 可空，合理年份范围校验 |
| `student_status` | VARCHAR(20) | 在校/休学/退学/毕业/其他等受控值 |
| `is_active` | BOOLEAN | 默认 true，逻辑停用标记 |
| `created_at` | TIMESTAMPTZ | 默认当前时间 |
| `updated_at` | TIMESTAMPTZ | 每次修改更新 |

#### `student_changes` 学籍异动

| 字段 | 类型 | 规则/说明 |
|---|---|---|
| `id` | BIGSERIAL | 主键 |
| `student_id` | BIGINT | 外键关联 `students.id` |
| `change_type` | VARCHAR(30) | 受控异动类型 |
| `effective_date` | DATE | 异动生效/发生日期，按业务确认字段语义 |
| `change_reason` | VARCHAR(500) | 可空；避免录入不必要敏感信息 |
| `record_status` | VARCHAR(20) | draft/pending_review/confirmed/returned |
| `source_batch_id` | BIGINT | 可空，导入来源批次 |
| `source_row_number` | INTEGER | 可空，原始文件行号 |
| `is_active` | BOOLEAN | 默认 true |
| `created_at` | TIMESTAMPTZ | 默认当前时间 |
| `updated_at` | TIMESTAMPTZ | 每次修改更新 |

#### `import_batches` 导入批次

| 字段 | 类型 | 规则/说明 |
|---|---|---|
| `id` | BIGSERIAL | 主键 |
| `batch_code` | VARCHAR(40) | 唯一批次编号 |
| `source_filename` | VARCHAR(255) | 原始文件名，不含绝对路径 |
| `file_sha256` | CHAR(64) | 文件哈希，用于发现重复文件 |
| `target_type` | VARCHAR(30) | students / student_changes |
| `total_rows` | INTEGER | 总行数 |
| `valid_rows` | INTEGER | 通过校验的行数 |
| `invalid_rows` | INTEGER | 异常行数 |
| `batch_status` | VARCHAR(20) | uploaded/validated/imported/failed |
| `created_by` | VARCHAR(150) | 测试阶段可记录 Appsmith 用户标识；生产前应确认身份映射 |
| `created_at` | TIMESTAMPTZ | 默认当前时间 |
| `finished_at` | TIMESTAMPTZ | 可空 |

#### `import_issues` 导入异常

| 字段 | 类型 | 规则/说明 |
|---|---|---|
| `id` | BIGSERIAL | 主键 |
| `batch_id` | BIGINT | 外键关联 `import_batches.id` |
| `row_number` | INTEGER | 原文件行号 |
| `field_name` | VARCHAR(100) | 出错字段 |
| `issue_code` | VARCHAR(50) | 受控异常代码 |
| `severity` | VARCHAR(20) | error/warning |
| `issue_message` | VARCHAR(500) | 简明说明，不放入多余个人信息 |
| `issue_status` | VARCHAR(20) | open/resolved/needs_review |
| `created_at` | TIMESTAMPTZ | 默认当前时间 |

#### `operation_logs` 操作记录

| 字段 | 类型 | 规则/说明 |
|---|---|---|
| `id` | BIGSERIAL | 主键 |
| `actor` | VARCHAR(150) | 操作者标识 |
| `action` | VARCHAR(50) | create/update/deactivate/import/export 等 |
| `object_type` | VARCHAR(50) | students/student_changes/import_batches 等 |
| `object_id` | VARCHAR(80) | 被操作对象 ID |
| `result` | VARCHAR(20) | success/failed |
| `details` | JSONB | 仅记录必要元信息，避免存完整敏感数据 |
| `created_at` | TIMESTAMPTZ | 默认当前时间 |

### 7.3 关键约束

- `students.student_no` 唯一且非空。
- `student_changes.student_id` 必须存在于 `students`。
- `import_issues.batch_id` 必须存在于 `import_batches`。
- 导入采用事务处理；同一文件哈希重复出现时提示用户，是否允许再次导入须由用户确认，并执行重复行保护。
- 所有业务列表默认只展示 `is_active = true` 记录，管理员可切换查看停用记录。
- 所有 SQL 查询使用参数化变量，不允许把用户输入直接拼接到 SQL 字符串。


## 8. Dify 集成规格

### 8.1 第一期集成

- 在 Dify 创建一个校园制度问答/业务辅助应用。
- 以 Appsmith 的 REST API 数据源调用 Dify 对话或工作流 API。
- Dify API 地址通过配置项保存；API Key 放在服务端安全配置中。
- AI 提示词必须明确：对学校制度问题，优先基于知识库材料回答；资料不足时要明确说不知道/需人工确认；不编造学校制度、不代替正式审批。
- AI 输入只允许一般问题、公开制度或虚构数据；禁止自动附带当前学生表格/详情。
- AI 返回内容展示“AI 生成，需人工核实”的提示。

### 8.2 第二期可扩展能力

- 使用 Dify HTTP Request 节点调用受控业务 API。
- API 必须有身份鉴别、字段白名单、返回行数限制、超时控制、审计记录和限流。
- 只读查询优先返回聚合统计或最小必要字段，不把整张学生表发送给模型。
- 写入采用提案模式：AI 输出拟修改字段与理由 → 页面展示差异 → 用户确认 → 业务接口再次校验并执行。
- 不把数据库管理员凭证、任意 SQL 执行能力或 unrestricted CRUD 工具提供给 Dify。

### 8.3 Dify 验收场景

1. 可以回答一条测试制度文档中明确写出的规则，并指出依据。
2. 对知识库没有的信息，回答“当前资料未提供，需人工核实”，不虚构答案。
3. Dify 暂停/超时时，学生信息管理、异动 CRUD、导入和导出仍然可用。
4. 在浏览器开发者工具和页面源码中无法找到 Dify API Key。
5. 第一阶段 AI 助手不会触发业务数据库写入。


## 9. Docker 部署与运行要求

### 9.1 本地目录建议

```text
campus-data-ai/
├─ README.md
├─ .gitignore
├─ .env.example
├─ deploy/
│  ├─ appsmith-postgres/       # 本地业务库与 Appsmith 的 Compose 配置/说明
│  └─ dify/                    # 按 Dify 官方仓库提供的 Docker Compose 配置部署
├─ import-api/                 # 可选：轻量 Excel 导入校验服务
├─ sql/
│  ├─ 001_schema.sql
│  └─ 002_seed_demo.sql
├─ docs/
│  ├─ PRD.md
│  ├─ TEST-PLAN.md
│  └─ SECURITY-CHECKLIST.md
└─ samples/
   ├─ students_demo.xlsx
   └─ student_changes_demo.xlsx
```

不得将真实数据、密钥、`.env`、备份文件或含敏感信息的导入文件提交到 Git。`.env.example` 仅保留变量名与示例占位符。

### 9.2 部署规则

- Windows 安装 Docker Desktop 并启用 WSL2；源代码和容器绑定文件优先放在 WSL2 Linux 文件系统中，或按官方文档验证 Windows 路径性能与权限。
- Appsmith 使用社区版容器镜像时，选择明确的发布标签并记录版本；不要直接使用不固定的 latest。
- Dify 使用其官方仓库当前发布的 Docker Compose 部署文件，保留其所需内部依赖，不将 Dify 内部库改造成校园业务库。
- PostgreSQL 使用官方镜像和持久化卷，设置强密码；数据库端口默认不对局域网/公网暴露。Appsmith 通过 Docker 内部网络访问数据库。
- Appsmith、Dify 如发生主机端口冲突，修改官方支持的端口环境变量，并在 README 记录最终访问地址。
- `.env`、密钥和密码不写入 YAML 明文仓库文件；至少通过环境变量文件管理，并限制访问权限。
- 初期仅绑定本机可访问的地址；不得直接开放公网或路由器端口。
- 建议本机至少有 16 GB 内存再同时运行多个服务；Appsmith 官方基线配置约为 2 vCPU/8 GB，Dify 官方快速启动最低要求约为 2 CPU/4 GiB，实际合并运行需求会更高。若硬件不足，先按阶段分别启动测试。运行本地模型需另行评估，不能默认能流畅运行。

### 9.3 常用操作必须写入 README

- 检查 Docker 版本与 Compose 版本。
- 启动、停止、查看状态、查看日志。
- 首次初始化 Appsmith 与 Dify。
- PostgreSQL 备份与恢复。
- 更新容器时如何固定版本、备份、升级和回滚。
- 数据文件与持久化卷所在位置。
- 常见端口冲突和容器间连接错误的排查方式。

### 9.4 备份和恢复

- 本地测试：每次进行数据库结构变更前备份一次；实现 `pg_dump` 备份及恢复演练。
- 校内试点目标：每日自动备份，备份文件加密或存放在有访问控制的位置；至少每月进行一次恢复验证。
- 不将备份保存在唯一的数据库容器可写层；应使用持久化目录并考虑独立备份位置。
- 生产备份保留周期、是否加密、恢复时间目标（RTO）与可接受数据丢失窗口（RPO）需由学校确认。


## 10. 非功能要求

### 10.1 易用性

- 界面中文化，字段名称采用教师日常语言，不在页面直接暴露数据库字段名。
- 所有危险操作有确认弹窗；错误信息说明具体字段和修正方向。
- 表格有空数据、加载中、失败重试和无权限等状态。
- 电脑浏览器优先，主要页面在 1366×768 分辨率可正常操作；不要求一期移动端适配。

### 10.2 性能

- 采用分页和服务端筛选，不一次性把全表拉进浏览器。
- 测试数据规模：学生 10,000 条、异动 20,000 条、导入文件 10,000 行。
- 在开发电脑资源足够的前提下，常规分页查询目标 3 秒内返回；具体性能取决于机器和容器资源。
- Excel 导入需要显示处理进度或阶段状态；不得因校验失败使 Appsmith 整个页面无响应。

### 10.3 可靠性

- 关键数据库写入使用事务。
- 保存失败要清楚提示，不得误显示为成功。
- 不重复提交同一个按钮操作；提交时禁用按钮或使用幂等/重复检测措施。
- 数据库/AI 服务失联时显示可理解错误，并允许非依赖模块继续使用。

### 10.4 安全与隐私

- 本地 MVP 只能使用虚构数据。
- 真实数据接入前须有学校授权、数据范围确认和安全评审。
- 按最小必要原则采集字段；禁止将学生数据、数据库密码、Dify Key 提交到公共代码仓库。
- 数据库采用最小权限账号；删除使用逻辑停用；操作日志可追溯。
- 生产环境需要 HTTPS、访问控制、网络隔离、备份加密/访问控制以及日志保留策略。
- Dify 的外部模型、嵌入模型、文件解析服务或工具调用可能产生外发数据；部署和提示词需通过实际数据流测试确认。
- 不把“去掉姓名”视为充分匿名化；学号、班级、异动原因、组合字段仍可能识别个人。

## 12. 分阶段实施计划

### 阶段 0：环境与仓库初始化

**产出：** 新项目目录、README、版本清单、`.env.example`、`.gitignore`、Docker/Compose 环境检查报告。  
**任务：** 检查 Windows/WSL2/Docker；确认磁盘和内存；选择 Appsmith 与 Dify 稳定发布版本；不安装本地模型。

### 阶段 1：业务数据库和基础页面

**产出：** PostgreSQL schema、虚构 seed 数据、学生信息页、学籍异动页、工作台首页。  
**任务：** 创建表与约束；在 Appsmith 配置只拥有必要权限的数据库账号；完成 CRUD 和筛选；不接入 Dify。

### 阶段 2：导入、异常与导出

**产出：** Excel/CSV 模板、导入向导、异常列表、导入批次报告、导出功能、测试报告。  
**任务：** 先确认 Appsmith 原生能力；若不能可靠处理 XLSX，则实现最小范围 Campus Import API；完成重复检测、事务和恢复测试。

### 阶段 3：Dify 接入

**产出：** Dify 问答应用、Appsmith AI 页面、密钥配置说明、断连测试。  
**任务：** 先用公开/虚构资料建知识库；Appsmith 服务端调用 Dify API；不让 Dify 读取/写入业务数据库。

### 阶段 4：校内试点前安全准备

**产出：** 安全检查表、数据字段审批表、部署拓扑图、备份/恢复演练记录、权限测试报告。  
**任务：** 与学校信息中心及业务部门确认真实数据范围、账号权限、服务器位置、网络访问、模型/数据是否外发、日志保留、备份和责任人。若权限模型不足，先增加受控业务 API，再允许真实数据使用。

### 阶段 5：后续扩展（不属于一期承诺）

- 学工更多模块：学生异动统计、批量报表、材料归档。
- 教务模块：课程、班级、学籍相关查询（需业务部门确认数据模型与来源）。
- 财务只作为独立后续评估，不把财务数据与学生资料无边界混用。
- Dify 只读业务 API、经用户确认的写入建议。
- 如学校需要统一账号，评估学校既有身份认证/OIDC/LDAP 能力。
- 如并发或可用性需求增长，再评估 Linux 服务器、HTTPS 反向代理、集中日志和容器编排。


## 13. 风险、依赖与未决问题

| 风险/问题 | 影响 | 应对方式/责任方 |
|---|---|---|
| Appsmith 自托管实际权限能力与版本不一致 | 可能不满足学工/教务的隔离要求 | 开发阶段先测试；管理员验证版本功能；真实数据接入前必须完成授权测试 |
| Excel 字段来源不一致 | 导入失败或数据冲突 | 为每类表建立模板、映射和异常报告；业务方负责确认规则 |
| Dify 模型或嵌入服务外发内容 | 学生数据泄露风险 | 第一阶段不发真实数据；信息中心审批模型与数据流；必要时评估本地模型 |
| Windows 电脑资源不足 | 多服务启动失败或速度慢 | 检查硬件；分阶段启动；不默认运行 Ollama |
| 开源项目许可/版本变化 | 影响再分发、商用或升级 | 锁定版本并记录许可证；学校正式采购/交付前重新核查项目许可证和依赖 |
| 未开放青果系统 API | 无法实时同步 | 一期只做授权 Excel 导入/导出，不承诺自动同步 |
| 数据库备份不完整 | 数据丢失 | 实施 pg_dump、恢复测试和独立备份存储 |
| 共享数据库账号导致越权 | 真实数据风险 | 本地 MVP 只用虚构数据；生产前完善用户到数据权限的验证机制或添加受控 API |

需要由学校/项目负责人确认的事项：

1. 校内试点使用哪些字段；哪些字段明确禁止录入。
2. 学工、教务的具体角色和数据可见范围。
3. 是否允许使用外部模型 API；如不允许，是否有经批准的本地/企业模型方案。
4. 校内服务器、网络访问方式、备份位置和数据保留期限。
5. 数据导入失败后是整批回滚，还是允许有效行先入库；一期默认整批事务提交，异常行不导入。

9. **不要使用 `latest` 固定正式部署。** 记录使用的镜像标签/版本、数据库版本、配置修改和升级方案。
