# ADR-001：Excel 表头识别与字段映射采用规则，不接入大模型

- **状态**：已采纳（Accepted）
- **日期**：2026-10-20
- **决策者**：项目负责人
- **影响范围**：`import-api` 的全部解析与映射逻辑；前端导入页的交互设计
- **相关文档**：`docs/IMPORT-API.md`、`docs/IMPORT-MAPPING-TEST.md`、`docs/DATA-DICTIONARY.md`

---

## 1. 背景

第一阶段导入要求 Excel 表头与系统字段**完全一致**，否则直接返回 `COLUMN_MAPPING_REQUIRED`。
实际收到的文件来自不同学院、不同系统（如强智教务导出），表头写法各异（`学生编号`/`学号`、`二级学院`/`学院`），且存在标题行、空行、多工作表。要求用户逐个改表头不可接受。

需要决定：**用规则解决，还是调用大模型 API 解决。**

---

## 2. 决策

**当前采用本地规则方案，不接入任何大模型或外部 AI API。**

需要区分两类“API”：

| 类型 | 是否使用 | 说明 |
|---|---|---|
| **业务 API**（系统自己的 FastAPI） | **使用** | React 页面通过 `/api/*` 调用预览、校验、提交接口，这些是内部后端，不是外部 AI 服务 |
| **AI 模型 API**（OpenAI / DeepSeek / Dify 等） | **不使用** | 解析过程中没有任何出网请求 |

已验证：`import-api/app` 与 `import-api/scripts` 中不存在 `requests`、`httpx`、`aiohttp`、`openai`、`dify` 等调用；依赖清单仅为 fastapi、uvicorn、pandas、openpyxl、pandera、psycopg、python-multipart、pydantic。

---

## 3. 当前方案的具体实现

| 环节 | 实现方式 |
|---|---|
| Excel / CSV 解析 | openpyxl（.xlsx/.xlsm）、pandas（含 CSV）；不依赖任何模型 |
| 工作表选择 | 遍历所有工作表，逐表在前 15 行内为每一行打分（命中别名数 + 必填字段数×2 + 数据行数）；多个表都可用时置 `needs_sheet_choice`，由用户确认，不静默选择 |
| 表头行定位 | 同上打分；用户可手动修改表头行号，改后重新解析 |
| 字段映射 | 三层：① 别名表完全相等（1.0）；② 字符串包含（0.78）；③ `difflib.SequenceMatcher` 相似度 ≥ 0.82（模糊） |
| 冲突处理 | 同一字段被多列命中时保留置信度最高者，其余标记 `conflict`，冲突未解决禁止校验与提交 |
| 未知列 | 保留为 `unmatched`，不强行分配字段，前端显示「不导入此列」 |
| 必填缺失 | 返回 `missing_required`，批次状态 `failed`，不允许继续 |
| 人工优先 | 手动指定的映射优先于自动结果：会解除原列占用，避免“改了映射却仍写旧列” |
| 重新解析 | 调用 `POST /imports/{id}/remap`，复用暂存文件，不需要重新上传 |
| 落库前校验 | 映射只解决列名差异；枚举、长度、日期、学号重复、学生存在性等规则**全部保留** |

---

## 4. 为什么不接入大模型

1. **结果可解释**：每一列为什么匹配、走的是精确/包含/模糊哪条规则、置信度多少，都能逐条说明。出现问题时可以定位到别名表或阈值，而不是“模型觉得”。
2. **无外部模型调用**：解析全程在本地容器内完成，不依赖网络状态、不需要 API Key、不会因外部服务限流或故障中断导入。
3. **成本与运行依赖低**：毫秒级完成，零调用费用；部署时不需要额外模型服务、显存或网络出口。
4. **学生数据不必因字段识别而外发**：表头与数据都留在本地。系统中已出现含身份证号、联系电话、家庭住址的表格，任何外部调用都会扩大数据暴露面。

补充说明：不接模型**不等于**系统没有 API。业务功能仍由内部 FastAPI 提供，前端通过 `/api` 代理访问，只是不调用外部大模型服务。

---

## 5. 当前方案的局限

| 类别 | 未支持 / 未验证 |
|---|---|
| 文件格式 | `.xls`（旧二进制格式）不支持，仅 `.xlsx` / `.xlsm` / `.csv` |
| 表头结构 | 多层（合并）表头不支持；合并单元格仅在左上角有值，可能造成必填缺失 |
| 工作簿保护 | 加密或密码保护的工作簿无法读取 |
| 表头位置 | 表头不在前 15 行时无法自动定位，需手动指定行号 |
| 语义差异 | 字面无关但业务等价的情况无法自动识别，例如「考生号」→ 学号（相似度仅 0.4），需人工指定 |
| 浏览器兼容 | 仅验证 Chromium 153；**Firefox / Safari / 移动端未验证** |
| 压力场景 | 接近 10 MB / 10,000 行上限的大文件、多人并发提交同一批次，**均未验证** |

---

## 6. 未来如果引入 AI：必须遵守的边界

仅当规则确实无法处理某类列名时，才考虑**可选的** AI 字段推荐，且必须满足：

1. **只发送必要的列名**，绝不发送学生行数据、身份证号、电话、家庭住址等字段内容。
2. 模型**只输出候选字段与理由**，最终由用户在页面上确认，不得自动应用。
3. 模型推荐**不能绕过**现有业务校验、权限检查与提交流程；它只影响“选哪个字段”，不影响“数据是否合法”。
4. **默认关闭**，并在界面明确展示“本次识别将向外部服务发送哪些内容”。
5. 接入前须完成：学校数据安全要求评估、外部服务条款与部署条件确认、数据流向说明留档。

---

## 7. 重新评估的条件

出现以下任一情况时，重新讨论本决策：

- 规则未识别列的比例在真实文件中持续超过 20%；
- 反复出现语义等价但字面无关的列名（如考生号、学籍辅号），且人工指定成为常态；
- 学校明确允许外发数据或提供可离线部署的模型服务；
- 出现必须理解表格结构语义才能处理的场景（如跨表关联、非结构化说明）。

---

## 8. 采用日期与结论

- **采用日期**：2026-10-20
- **当前结论**：规则方案满足现阶段（虚构数据、本地验证）需求，已通过 11 项接口测试与 20 项浏览器验收。
- **一句话**：先让规则处理它擅长的（同义不同写），把规则处理不了的交给人工；AI 解决的是规则够不着的问题，而不是替代已经可测试的规则。
