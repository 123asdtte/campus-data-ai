# 安全检查清单

**适用范围：** 阶段 1 本地验证（虚构数据）
**结论：** 本阶段可以运行，但**不允许**接入真实学生数据。接入前必须完成第 9 节全部项目。

---

## 1. 数据边界

- [x] 全库为虚构数据（姓名由字库组合生成，学号为 `DEMO` / `SMPL` / `TESTCRUD` 前缀）。
- [x] 表结构不包含身份证号、手机号、家庭住址、家庭成员等敏感字段。
- [x] 未从任何旧系统、资料库或线上环境导入真实数据。
- [ ] **真实数据入口尚未关闭**：系统没有强制拦截机制，靠人工纪律。接入前必须增加导入前置校验（如文件来源白名单）或部署到隔离环境。

## 2. 身份与审计

审计由数据库触发器在同一事务写入，`campus_app` 对 `operation_logs` 只有 SELECT 权限，无法篡改。

| 场景 | `actor_user_id` | `actor_db_role` | 结论 |
|---|---|---|---|
| Import API 写入（关闭态） | 请求头 `X-Actor` 的值 | `campus_app` | 可追溯，但**身份未认证** |
| Import API 写入（开启态） | 验签通过的 `X-Internal-User` | `campus_app` | 可信身份，与登录用户一一对应 |
| Appsmith 直连写入 | `NULL` | `campus_app` | **已停服务（R2）**，该路径不再存在 |
| 运维直接执行 SQL | `NULL` | `session_user` | 仅能识别数据库账号 |

已修正的实现缺陷：触发器原使用 `current_user`，在 `SECURITY DEFINER` 下会记录为函数属主（`campus_dba`），已改为 `session_user` 并复测通过。

**必须补足的三点：**

1. `X-Actor` 是客户端自报字段，任何人可伪造；开启态已由 `X-Internal-*` 签名取代，关闭态仅限虚构数据阶段。
2. Appsmith 已按 R2 停服务（2026-10-22），不再直连数据库；恢复时必须改回「受控 API」路径，不得直接复用可写账号。
3. `actor_user_id` 为空时应在页面上显式提示「该记录无法追溯到具体操作人」，不能默认为可信。

## 3. 权限模型

| 账号 | DELETE 业务表 | UPDATE 审计表 | 结论 |
|---|---|---|---|
| `campus_app` | 禁止（唯一例外：`import_issues`） | 禁止 | 符合最小权限 |
| `campus_ro` | 禁止 | 禁止 | 只读 |

- [x] Appsmith 未使用 `campus_dba`。
- [x] 业务记录只做逻辑停用，不提供物理删除入口。
- [x] **Appsmith 已按 R2 停服务（2026-10-22）**：容器停止、compose 移除、8081/8443 无监听，可写账号暴露路径已阻断；账号本身仍存在，留待 PR-B 最小权限治理。

## 4. 密钥与凭据

- [x] `.env` 已列入 `.gitignore`，仓库中只有 `.env.example` 占位符。
- [x] 代码中无硬编码密码；`DATABASE_URL` 由环境变量注入。
- [x] Appsmith 数据源凭据由服务端加密保存，不下发浏览器。
- [ ] **Dify API Key 若未来接入，必须放在数据源的 Authentication 配置中**；放入 query header 会随应用 DSL 下发到浏览器，属严重泄露。
- [ ] `APPSMITH_ENCRYPTION_PASSWORD` / `SALT` 一旦初始化不可更改，需纳入密钥管理台账。

## 5. 网络边界

- [x] 三个服务端口均绑定 `127.0.0.1`（8081 / 8443 / 55432 / 8010），未使用 `0.0.0.0`。
- [x] 容器间通过 `campus-net` 内部网络通信，数据库不监听公网。
- [x] 未配置端口转发或内网穿透。
- [ ] 本地环境无 TLS；校内试点必须由反向代理提供 HTTPS。

## 6. 备份与恢复

- [x] 备份文件写入 `backups/`（已 gitignore），与数据卷分离。
- [x] 完成一次独立库恢复演练（`docs/archive/TEST-PLAN.md` AT-016）。
- [ ] 备份未加密。接入真实数据后必须加密或存放于受控位置，并明确保留周期。
- [ ] 尚未配置自动备份与恢复验证周期（试点阶段目标：每日备份、每月演练）。

## 7. 导入文件处理

- [x] 上传文件保存在卷 `campus_uploads`，提交成功后删除（`KEEP_UPLOAD_FILES=false`）。
- [x] 暂存文件名由服务端生成批次号，不使用用户文件名，避免路径穿越。
- [x] 单文件 10 MB / 10,000 行限制，防止超大文件拖垮服务。
- [ ] 若开启 `KEEP_UPLOAD_FILES=true`，原始文件将长期保留且含个人信息，需单独审批。

## 8. Dify 与外部服务（阶段 2）

- [ ] Dify 未部署，当前不存在任何模型外发路径。
- [ ] Dify 许可证为基于 Apache-2.0 的附加条款版本，涉及多租户服务与前端标识限制；校内自用部署不受影响，**若未来做 SaaS 或再分发须重新审查**。
- [ ] 接入前需确认：模型端点、嵌入模型、文件解析是否外发数据；知识库仅使用公开或已批准材料。
- [ ] iframe 嵌入 WebApp 与 API 调用是两条独立路径：前者由 Dify 处理会话，后者须在服务端保存 Key 并限制调用范围。
- [ ] 嵌入 Dify 页面**不等于**获得学校身份与数据权限，需单独验证认证与访问控制。

## 9. 接入真实数据前的阻断项（全部完成才可继续）

1. 学校书面授权与数据范围确认（哪些字段可录、哪些禁止）。
2. 身份认证方案落地：Appsmith 不再直连业务库，改为受控 API + 统一身份。
3. 行级/字段级权限验证，并通过越权测试（修改请求参数、SQL 参数）。
4. 网络与传输：内网部署、HTTPS、访问控制、日志保留策略。
5. 备份加密、异地存放、恢复演练记录。
6. 审计链路验证：任意一条业务变更都能定位到具体操作人。
7. 数据分类分级与保留期限确认，明确删除与归档流程。
8. 安全评审通过并留档。
