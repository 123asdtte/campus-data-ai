## D-4 死代码：`_read_frame` / `_map_columns`

**状态：已实施。** 两个函数与随之失去引用的 `import io` 已删除；剩余引用只出现在测试注释里，随 D-2 一并改写。

**现状**

| 位置 | 内容 | 调用方 |
|---|---|---|
| `import-api/app/service.py:57` | `_read_frame()`：按后缀分派 + 三编码兜底 + `仅支持 .xlsx / .csv` | **零**（全仓库仅测试注释里提到） |
| `import-api/app/service.py:84` | `_map_columns()`：精确别名映射 + 补齐可选列 | **零** |

活代码路径是 `parsing.load_frame()`（`service._prepare():332` 调用）。`_normalize_frame()` 仍在用（`service.py:341`，且 `test_validation.py` 有直接用例），**不在删除范围**。

**为什么必须处理**

这两个函数不是无害的遗留物，它们是**判断陷阱的来源**：D-2 的「扩展名白名单」和 D-3 的「三编码兜底」都在这段死代码里，任何人读代码都会得出「已经做了校验」的结论——本项目的 §10-2、§10-3 两条误判就是这么来的。

**选项**

| | 做法 | 影响 |
|---|---|---|
| A（推荐） | 删除两个函数 | 约 60 行净减少，零行为变化 |
| B | 保留并加 `# deprecated, 无调用方` 注释 | 陷阱仍在，下一个人还会读错 |
| C | 保留，改成文档里指明「历史实现」 | 同上，且增加文档维护面 |

**验证**：`python -m pytest`（本地无库也应 106 passed）；`grep -rn "_read_frame\|_map_columns" import-api/` 只应剩测试文档字符串里的引用，需一并改写为 `parsing.load_frame`。

**不改的后果**：每条指向「白名单已生效」的结论都不可信；后续每加一个后缀判断都要在两套实现里挑一套，读代码的人永远不知道哪套在跑。

## D-1 sidecar `.mapping.json` 残留

**状态：部分实施。** 提交路径已改为 `_remove_staged()`（同删暂存文件与 sidecar，`test_staging.py::TestSidecarCleanup` 由 xfail 转为正式断言，`test_parsing_edge.py::TestStagedCleanup` 补 3 条纯 FS 用例）。**孤儿文件的一次性清理脚本未做**——存量环境仍需要 `find UPLOAD_DIR -name '*.mapping.json' -delete` 手动清一次。

**现状**

- 预览时写：`service.py:395` → `_write_sidecar()`（`:294`），落在暂存文件旁，命名 `_sidecar_path()`（`:290`）＝同目录同名换后缀。
- 提交后删：`commit_batch` 末尾 `service.py:796-805` 只 `os.remove(staged_path)`，**不删 sidecar**；随后把 `import_batches.staged_path` 置 NULL。
- 后果链：文件留下了、数据库里的路径没了 → 无法从库里反查孤儿文件，只能扫盘。

**量级**：每次「预览成功」产生 1 个 sidecar（约几百字节）；即使最终没提交也留。按 100 批次/天、只算成功导入的，一年 ≈ 3.6 万个碎文件。它不影响功能，但会让 `UPLOAD_DIR` 无法按「空即无残留」做验收。

**选项**

| | 做法 | 影响 |
|---|---|---|
| A（推荐） | 删除暂存文件时一并删除 sidecar；`keep_upload_files=true` 时两者都保留 | 3 处改动（删除点、`keep` 分支、日志），零接口变化 |
| B | A + 一次性清理脚本（扫 `UPLOAD_DIR`，删无对应暂存文件的 sidecar） | 多一个 `import-api/scripts/`，可离线跑，适合存量环境 |
| C | 加 TTL 定时任务 | 引入调度依赖，与当前「无后台任务」的架构不符，不建议现在做 |
| D | 维持现状，只写进文档 | 磁盘持续增长，验收指标无法定义 |

**推荐**：B。A 是必须的，脚本把存量环境也收拾干净；不引入定时任务。

**验证**：现有 `test_staging.py` 里那条 `xfail(strict=True)`（`test_提交成功后sidecar应一并清理`）会 XPASS → 删标记转正式断言。这正是当初写 strict 的目的。

**未实测**：清理脚本在「暂存文件已被手工删除、只剩 sidecar」时的行为，需要真库/真实目录跑一次；脚本需支持 `--dry-run`。

## D-2 扩展名白名单未生效

**现状**

- `parsing._is_xlsx()`（`:65`）只判断是否 `.xlsx/.xlsm`；`load_frame()`（`:158`）据此二分：是 Excel 走 `read_excel`，**其余一切**走 `read_csv`。
- `service.create_batch()`（`:389`）给暂存文件定后缀时也是同一个二分：非 xlsx/xlsm 一律存成 `.csv`。
- 「仅支持 .xlsx / .csv」这句话只存在于死代码 `_read_frame()` 里 → 白名单**实际未生效**，已在 `test_meta_and_files.py::test_未知后缀按内容识别` 固化为现状。

**实测影响（本机用真实字节跑 `parsing.load_frame` 的结果，不是推测）**

| 上传文件 | 实际发生 | 用户看到 |
|---|---|---|
| `名单.txt`（内容是 CSV） | 正常解析、正常导入 | 成功（后缀不符但无害） |
| `名单.pdf` | 二进制按 CSV 解析成一列 `%PDF-1.4` + 7 行"数据" | `200 + status=failed + 缺少必需列`：批次建出来了、写进了上传目录（存成 `.csv`），用户得到一条失败批次，但**没人告诉他"这是 PDF 不是表格"** |
| `表格.xls`（OLE2 老格式） | 按 CSV 解析成一列控制字符、0 数据行 | `400 文件没有可导入的数据行` —— 提示指向"内容空"，而真实原因是"格式不支持" |
| 无后缀文件（内容是 CSV） | 按 CSV 解析 | 成功 |

也就是说**真正的问题不是"放行了 .txt"，而是把三种不同的失败（后缀错、格式老、内容空）收敛成了同一条含糊提示**，用户无法据此自查。


**选项**

| | 做法 | 影响 |
|---|---|---|
| A（推荐） | 白名单 `.xlsx/.xlsm/.csv`，其余在 `create_batch` 入口直接 400，`detail` 写明「仅支持 .xlsx/.xlsm/.csv，当前文件名 xxx」 | 2 处改动；`.txt` 由「成功」变「拒绝」、`.pdf` 由「静默建失败批次」变「当场拒绝」；已有两条现状固化用例需改写 |
| B | 维持按内容识别，把前端提示改成「支持 CSV/Excel 内容，后缀不限」 | 0 处代码改动，改 2 处文案；但 `.pdf` 仍会建出失败批次，`.xls` 的报错仍然误导 |
| C | 按内容识别 + 未知后缀给 warning，允许继续 | 需要新增 warning 通道（issue 只在批次上，无"全局提示"位置） |

**推荐**：A。理由：校内上传者不是技术人员，**拒绝时给出的理由必须能指导他下一步动作**；「后缀不支持」是他能自己修的问题，「没有数据行」不是。A 的代价是极少数"内容对、后缀错"的文件要改个名，而 `test_unknown_columns.csv` 这类正常 CSV 不受影响。

**改完之后要同步改的用例**：`test_parsing_edge.py::test_未知后缀按内容识别`、`test_meta_and_files.py::test_未知后缀按内容识别`（这两条是现状固化，改为断言 400，并把副标题改成「拒绝未知后缀」）。

**若批准 B 而非 A**：请同时在 PR 里删掉死代码里那句「仅支持 .xlsx / .csv」，否则文档、代码、用户体验三处继续各说一套。

## D-3 编码非法时静默替换

**现状**

`parsing.load_frame()`（`:182-186`）：

```python
raw = data.decode("utf-8-sig", errors="replace")   # 坏字节 → U+FFFD
try:
    raw = data.decode("gbk")                        # 尝试 GBK，失败则保留上面那份"替换过"的文本
except UnicodeDecodeError:
    pass
```

`_read_raw_rows()`（`:82-84`，用于表头分析）是同样的写法，所以**分析与读取的容错口径一致**——这点是对的，改的时候必须两边一起改，否则会出现「分析阶段识别的表头」和「实际读到的一行」不是同一份数据。

**实测三条走向（本机用真实字节跑 `load_frame`，三种坏法结果完全不同）**

| 坏法 | 实际发生 | 严重度 |
|---|---|---|
| 整份 UTF-16（Excel「Unicode 文本」常见） | `utf-8-sig` 替换出一堆 `U+FFFD` 与 `\x00`；`gbk` 解码"成功"但没有换行语义 → pandas 抛 `ParserError: new-line character seen in unquoted field` → **未捕获，HTTP 500** | 高（500，不是 400） |
| GBK 文件里表头行含一个非法字节（如 `0x80`） | 两种解码都失败 → 退回"替换过"的文本，**表头本身变成 `ѧ��`/`����`** → 自动映射全部失配 → `200 + status=failed + 缺少必需列` | 中（用户看不懂原因） |
| UTF-8 文件里**值**含坏字节（表头正常） | `学号` 变成 `S��001`，Pandera 只校验长度 1–32 与非空 → **校验通过、静默入库** | 最高（数据错了且看不出来） |

只有第三种是「静默写入错误数据」，但它恰恰是最容易发生的：从旧系统导出的 CSV 里混几个坏字节、表头却是好的。前两种虽然不是数据污染，但一个 500、一个提示含糊，都属于同一根因。


**选项**

| | 做法 | 影响 |
|---|---|---|
| A（推荐） | 严格解码：`utf-8-sig` → `gbk` → 都失败则 400「文件编码无法识别，请用 Excel 另存为 CSV UTF-8」 | 3 处（`load_frame`、`_read_raw_rows`、错误文案）；坏编码从「静默入库 / 500 / 提示含糊」三种结局统一成「400 + 可操作指引」，顺带消灭上表第一条的 ParserError 500 |
| B | 仍替换，但只要检出 `U+FFFD` 就 400 | 需要额外全表扫描；且"到底哪几行坏了"仍说不清 |
| C | 仍替换，但把该批次标 `warning` 并提示"N 行含无法识别的字符" | 需要 issue 级别与前端展示配合，成本最高 |
| D | 维持现状，文档写明「编码问题由用户保证」 | 乱码数据入库且不可追溯，不建议 |

**推荐**：A。与 D-2 同一个原则——**静默降级比拒绝更贵**。A 的实现是「把 `errors="replace"` 去掉」，改动量最小、语义最清晰。

**风险与缓解**：极少数 GBK 文件里混入个别非法字节时会被整份拒绝（现状是"能进但有一行乱码"）。缓解：错误文案里给出「用 Excel 另存为 CSV UTF-8」的明确指引；如需宽容，可在同 PR 加一个显式开关（默认严格），但**不建议默认关闭**。

**改完之后要同步改的用例**：`test_parsing_edge.py::test_非法字节被替换为替换字符而不是报错`（改为断言 `ServiceError`），并在 `test_meta_and_files.py` 增加一条 HTTP 层用例（坏编码 CSV → 400 + 指定文案）。
